## 우선 보강 사항

### F01 · 우선 — 작업 완료와 제품 릴리스 완료를 분리해야 한다 (R05)

`roles/_team-workflow.md:268`의 §6.3은 작업별 완료 기준으로 읽히지만, 전체 인수 조건을 덮는 테스트와 전 게이트 통과를 함께 요구한다. 테스트설계는 MVP 전체의 RED 테스트를 먼저 준비한다. 이 규칙을 문자 그대로 적용하면 아직 만들지 않은 기능 때문에 초기 코어 PR의 완료·리뷰·머지가 막힐 수 있다.

**보강안:** 작업 ID별 승인된 US/AC/TC 범위, 관련 비기능 검사, 기존 완성 기능의 회귀 검사를 묶어 `작업 완료`를 판정한다. `릴리스 완료`는 승인된 제품 범위 전체에 대해 판정한다. 두 결과는 이름과 근거를 구분하고, 임의 `--only`의 PARTIAL_PASS를 작업 완료로 승격하지 않는다. 미구현 요구는 추적표에 미완료로 남기며 테스트 삭제·skip으로 숨기지 않는다.

**유지할 정책:** 작업 범위 안의 차단 결함·MEDIUM 0건과 릴리스 전체의 차단 결함·MEDIUM 0건은 유지한다. 작은 PR을 허용하기 위해 MEDIUM을 허용해야 하는 것은 아니다. 문제는 완료 판정의 대상 범위다.

**확인할 사례:** AC-1만 구현된 작업은 관련 검사와 기존 회귀를 통과하면 작업 완료가 될 수 있다. AC-2가 미구현이면 전체 제품 릴리스는 계속 차단되어야 한다.

### F02 · 우선 — 최종 릴리스 제어는 여전히 문서 규칙이다 (R03/R07)

FULL_PASS는 설정된 자동 검사의 성공을 뜻한다. 커밋·정책·아티팩트·양쪽 판정·결함·운영 승인의 일치를 검사하는 릴리스 실행기는 아직 없다. 3라운드 토론을 추가해도 이 공백은 메워지지 않는다.

**보강안:** 확정된 후보 SHA·검증 정책 해시·run ID·테스트 범위·아티팩트 digest·파트별 양쪽 판정·차단/미해결 결함·릴리스 승인·복구 근거를 하나의 릴리스 기록으로 연결한다. CD는 검사를 통과한 동일 아티팩트만 승격한다. 코드·정책·아티팩트 변경은 관련 판정을 무효화하고 재검증한다.

**확인할 사례:** PARTIAL_PASS, 다른 SHA/digest, Codex 근거 누락, 미해결 MEDIUM, 변경 후 옛 서명, 승인 누락은 모두 거부해야 한다. FULL_PASS와 서명만 존재해도 대상이 다르면 배포할 수 없어야 한다.

근거: `bin/team-gate`의 요약·판정, `roles/_team-workflow.md` §6.2·§7, `roles/배포.md`, 보완 결정 기록의 ‘다음 단계에 남는 제어’.

### F03 · 우선 — 토론 합의와 이견 기록의 서명을 구분해야 한다

공통 §3.2(`roles/_team-workflow.md:128`)는 모든 항목 해소 후에 페어 서명하며 남은 이견은 없음이라고 정한다. 반면 `templates/pair-discussion.md:32`는 같은 페어 서명에 `남은 이견: 없음 | <요약>`을 허용한다. 서명이 인계 조건으로 쓰이므로 이견이 남은 토론 기록을 합의된 산출물로 오인할 수 있다.

또한 `templates/review.md`에는 Codex 재확인 서명만 있고, 대상 작성자·Claude 1차 판정자·최종 양쪽 판정·라운드·차단 이견을 함께 기록하는 최종 계약이 부족하다. 본문 규칙을 읽으면 보완할 수 있지만 템플릿만 따라 쓰는 경우의 누락을 막아야 한다.

**보강안:**

- 합의/통과 서명은 양쪽의 최종 판정과 대상 버전, 남은 차단 이견 0건을 함께 기록한다.
- 이견 상태에서는 ‘양쪽 입장 기록 확인’으로 표시하고 합의·통과·인계 승인을 뜻하지 않도록 한다.
- 비차단 이견을 처리할 수 있다면 허용 조건·결정권자·후속 담당을 별도로 정한다. 후속 이월이 금지된 MEDIUM을 비차단으로 우회하지 않는다.
- 최초 검토에서 동의한 경우는 `0/3`, 상반된 항목의 회신·재검토 한 쌍을 1라운드로 명시한다.
- 동일 쟁점 ID의 산출물 버전 변경만으로 라운드를 초기화하지 않는다. 3라운드 종료 또는 근거 반복 시 다음 상태는 합동 리뷰/결정 대기다.

CR의 파트 간 1회 추가 교환(§4.3)과 파트 안 최대 3라운드는 서로 다른 제한이므로 적용 단위를 명시하는 편이 좋다.

### F04 · 필요 — 새 흐름에서 독립 검증의 근거를 구체화해야 한다

Claude가 먼저 제시하고 Codex가 검토하는 순서는 유지할 수 있다. 자기 대안을 제시하게 하는 규칙과 직접 재확인은 도움이 된다. 다만 Claude의 판정문을 본 뒤 대안을 하나 적었다는 사실만으로 독립 검증이 충분했다고 판단할 수는 없다.

**보강안:** Codex가 실제 검토한 코드/설정의 SHA·diff, 테스트/측정 명령·환경·결과, 확인한 오류 경로·반례·누락 범위를 기록하도록 한다. ‘문서 읽음’과 ‘측정 재실행’을 구분하고, 실행이 불가능하면 불완전 검증으로 기록한다. 자동 검사가 모두 성공했어도 추가로 발견된 결함은 반려 대상이다. 사람이 다른 페어라도 실제 산출물 작성자가 자기 결과의 최종 검증자가 되지 않게 작성자·판정자·검토자 ID를 구분한다.

이는 독립 초안이나 Codex 선제 판정으로 돌아가자는 제안이 아니다. 현재 순서 안에서 자기 근거로 판정했다는 사실을 확인 가능하게 만드는 보강이다.

근거: 공통 §3.1, `roles/품질.md`, `roles/성능.md`, `roles/보안.md`, `templates/review.md`.

### F05 · 필요 — 새 역할은 분량보다 반례·협업 경계를 보강해야 한다

운영신뢰성과 데이터관리 문서에는 이미 입력·산출물·완료 기준과 일부 반증 조건이 있다. 35줄이라는 길이 자체가 결함은 아니다. 다만 다른 역할처럼 정체성·비판 체크리스트·협업·Do/Don't를 명시하면 빠뜨리는 검증과 겸임의 책임 혼동을 줄일 수 있다.

| 역할 | 보강할 반증 사례 | 명확히 할 협업·금지 |
|---|---|---|
| 운영신뢰성 | 백업은 존재하지만 복원 실패, 복원 데이터 손상, 알림 미전달, 관측 수집 중단, 의존 서비스 장애, 롤백 후 SLO 미회복 | 성능은 측정·예산 판정, SRE는 상시 운영·복구; CD/배포 겸임자의 준비 선언만으로 운영 인수 완료 불가; 품질·성능·보안의 독립 검증과 사용자 승인 유지 |
| 데이터관리 | 마이그레이션 절반 적용·재시도 중복, 백필과 동시 쓰기 충돌, 구버전 읽기 실패, 삭제 데이터가 백업 복원으로 재등장, 이벤트 중복·순서 뒤바뀜 | 설계는 계약 승인, 코어/데이터는 구현, 통계는 측정 의미, 보안은 개인정보 통제; 데이터 정책·파괴적 변경을 독단 실행하지 않음 |

각 문서에 입력의 준비 기준, 검증 환경, 실행 근거, 실패 시 CR 대상, 독립 검증 수령자를 연결해야 한다. 특히 복구 실험은 두 파트가 서로의 완료를 기다리는 순환 의존이 되지 않도록 공동 실행 담당과 최종 판정 담당을 구분한다.

### F06 · 필요 — 제한시간·취소·중단 후 결과가 없다 (R09의 나머지)

옵션 파싱과 부분 실행 이력은 수정됐다. 그러나 게이트 명령이 멈추면 전체 실행도 계속 대기한다. 중단된 실행과 이전 `latest-full.md`를 구분하는 실행 상태도 없다.

**보강안:** 게이트별 제한시간, 취소 신호 처리, 자식 프로세스 정리, `TIMEOUT`/`CANCELLED`/`INCOMPLETE` 상태를 둔다. 진행 중 실행을 이전 성공과 구분하고, 릴리스에서 현재 대상의 완료된 근거만 인정한다. 제한시간 초과가 다음 검사를 막거나 성공으로 바뀌지 않게 한다.

**확인할 사례:** 무한 대기 명령·자식 프로세스를 만드는 명령·중간 취소·동일 작업 동시 실행에 대해 거짓 FULL_PASS와 고아 프로세스가 없어야 한다. 기존 성공 기록은 새 실행 실패를 숨기는 근거로 사용할 수 없다.

### F07 · 정리 — 결정 권한과 위임·작성 이력을 분리해야 한다

클로드가 지적한 결정 기록의 모호함은 문구 보강이 적절하다. 다만 실제 대화는 사용자가 선택을 요청했고 Codex가 선택·반영한 것이므로, 사용자가 정책 내용을 직접 명시적으로 승인했다고 새로 기록해서는 안 된다.

**권장 표기:** `결정권자: 사용자 / 선택 방식: 사용자의 정책 선택 위임에 따라 Codex가 선택 / 작성·반영: Codex / 별도 Claude 합동 승인: 해당 기록에는 없음`.

보완 기록의 94개는 당시 검증 결과이므로 틀린 이력은 아니다. 당시 결과를 95개로 덮어쓰기보다 클로드 수정 후 95개 통과를 후속 이력으로 추가한다. 조직 결정 표의 과거 Codex 주도 근거와 새 Claude 주도 결정의 근거도 ‘최초 결정’과 ‘변경 결정’으로 구분하면 읽기 쉽다.

## 조건부 보강

온라인 게임·서버 운영형 도구에는 운영신뢰성·데이터관리가 필요할 수 있다. 현재 서비스 3개 프로필에만 배정한 것은 선택한 범위와 일치하므로 바로 버그로 볼 수 없다. 게임의 네트워크·계정·결제·원격 저장·상시 서버 여부를 팀 구성 체크리스트에 넣고, 해당하면 사용자에게 두 파트의 정식 겸임 또는 전담 배정을 제안한다. 오프라인 게임이나 상태 없는 라이브러리에 무조건 두 파트를 추가할 필요는 없다.

1. F01 작업/릴리스 범위와 F03 서명 계약을 먼저 명확히 한다.
2. F02 릴리스 검사기와 F06 실행 중단 처리를 구현하고 거부 사례를 검증한다.

4. F07 결정 기록을 정리하고, 작은 서비스에서 CR·3라운드 이견·수정·재검증·승격·롤백까지 전 구간 파일럿을 수행한다.

‘최대 3라운드’, ‘Codex 근거 필수’, ‘미해결 이견의 인계 차단’은 현재 자동 검사로 강제되지 않는다. 도구 테스트 95개 외에 합의 즉시 성립·1/3/3라운드 후 미해소·근거 반복·한쪽 서명 누락·변경 후 옛 판정의 시나리오를 실제 두 CLI 인스턴스로 확인해야 한다. 운영 배포까지 승인한 테스트 요청으로 해석하지 않는다.
